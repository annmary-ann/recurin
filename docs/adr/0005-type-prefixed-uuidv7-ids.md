# 0005. Type-prefixed UUIDv7 IDs

- **Status:** Accepted
- **Date:** 2026-11-23
- **Issue:** #6

## Context

IDs appear everywhere people debug billing: API responses, webhook payloads, logs, support tickets and gateway metadata. A support engineer handed `0193a5f2-...` cannot tell whether it is a customer, an invoice or a payment. IDs also need to:

- be generated by the application, so an ID exists before the insert and can be used as an idempotency or correlation key;
- not leak business volume (sequential integers reveal how many invoices a platform issues);
- index well in Postgres. Random UUIDv4 keys scatter inserts across the B-tree and bloat indexes on large tables.

## Decision

Every public ID is a **type prefix plus a UUIDv7**, for example `cus_01JD8X...`, `sub_...`, `inv_...`, `pay_...`, `man_...`.

- **UUIDv7** is time-ordered, so new rows append near the end of the index, and IDs sort roughly by creation time.
- The prefix names the type. The API rejects an ID with the wrong prefix (`inv_` passed where `cus_` is expected) before any query runs.
- In Postgres the value is stored as a native `uuid`; the prefix is added and checked at the boundary by typed Go IDs (`CustomerID`, `InvoiceID`), so the compiler stops mixing them up.
- The text form encodes the UUID compactly (base32), keeping IDs short in URLs and logs.

## Alternatives considered

- **bigserial integers.** Compact and fast, but leak volume, collide across environments (test vs live) and need a database round trip to exist.
- **UUIDv4.** Unguessable but random, which fragments indexes on large tables, and still unreadable to humans.
- **ULID.** Similar properties to UUIDv7, but not a standard UUID, so it needs custom Postgres handling. UUIDv7 is now an RFC (9562) and supported by Postgres tooling.
- **Snowflake-style IDs.** Need worker-ID coordination, which self-hosters should not have to manage.

## Consequences

- IDs are readable in logs and tickets, and type confusion is caught by both the compiler and the API.
- Insert locality is good for the largest tables (usage events, postings, outbox).
- UUIDv7 reveals the creation time to anyone holding the ID. That is acceptable for billing objects, whose timestamps are returned by the API anyway.
- The prefix scheme is part of the public contract and cannot change after v1.
